# 第8节：为什么需要 G/P/T/C，而不是一个 U？

核心结论先说：

```
理论不证明“多个排序器一定优于 U”。
理论只给出：
若请求需要不同交互，条件计算可能值得研究。
```

------

## 8.1 最简研究对象

作者先把所有复杂东西拿掉：

```
完整合法输入 X
→ 一个排序器
→ 输出 top10
```

\(X\) 包含：

```
合法历史
明确需求
50候选原始图文
基础分数
```

然后问：

> 一个统一排序器，在相同训练、时间、内存、参数条件下，能不能解决全部问题？

如果能：

```
保留 U
不要强行拆成 G/P/T/C
```

这条原则很重要：

> 设计机制前，先尝试更简单的单模型替代。

所以 U 不是“弱 baseline”，而是必须认真比较的强替代。

------

## 8.2 区分两个问题：信息丢失 vs 模型能力不足

输入先经过表示：

\[ \psi(X) \]

例如：

```
完整历史
→ 只保留计数摘要
→ 评分器读取摘要
```

作者定义三种风险：

```
L_X*：
  读取完整 X 时，理论上最小错误

L_ψ*：
  只能读取压缩表示 ψ(X) 时，理论上最小错误

训练模型实际风险：
  有限网络、有限样本、优化后的错误
```

恒等式：

\[ \text{实际错误} = \text{表示损失} + \text{有限模型近似损失} + \text{训练损失} \]

对应：

| 项       | 人话                       |
| -------- | -------------------------- |
| 表示损失 | 压缩后事实已经丢了         |
| 近似损失 | 网络太小，表达不了最佳规则 |
| 训练损失 | 样本少、优化差、分布不匹配 |

重点：

```
模型效果差
不一定是信息丢了
也可能只是模型没学会
```

反过来：

```
加大模型
也不能恢复已经被 ψ 丢掉的信息
```

但注意：

```
压缩不一定坏
扩展文本不一定带来新信息
参数量相同不代表表达/费用相同
```

------

## 8.3 两个历史摘要的反例

文档构造：

```
H1 = {(1,1), (0,0)}
H2 = {(1,0), (0,1)}
```

如果摘要只记录两个属性各出现几次：

```
H1：
  属性1出现1次
  属性2出现1次

H2：
  属性1出现1次
  属性2出现1次
```

摘要完全相同。

但原始配对不同：

```
H1 有 (1,1)
H2 没有 (1,1)
```

如果最优推荐取决于是否出现 `(1,1)`：

```
完整历史可以区分
计数摘要不能区分
```

所以只读摘要的模型：

```
H1 和 H2 必须给同样排序
→ 至少有一个请求排错
```

这个例子证明：

```
某种压缩表示可能丢掉决策所需交互
```

不证明：

```
实际 G 的摘要一定丢信息
G 一定比 U 差
多个排序器一定必要
```

因为一个单模型仍可以在池化前保留配对关系：

```
先计算每个事件的属性交互
→ 再汇总
```

所以问题不是：

```
有没有多个网络
```

而是：

```
排序计算是否保留了决策所需交互
```

------

## 8.4 什么时候专门化和选择器才有意义？

第8.4节给三个必要条件。

### 条件1：评分必须利用正确交互

可能需要：

```
公共摘要
候选相关历史
局部图文
候选集合关系
```

对应：

```
G：公共摘要
P：候选查询历史
T：需求查询内容
C：候选集合交互
```

但同样功能也能由：

```
一个联合网络
一个统一模型内部的条件计算
```

实现。

所以：

```
模块名称不构成理论优势
```

### 条件2：不同请求需要不同计算

如果所有请求都适合 PT：

```
固定 PT 可能最好
```

如果所有请求都适合 C：

```
固定 C 可能最好
```

只有存在：

```
请求A：STOP 足够
请求B：C 有用
请求C：PT 有用
```

动态 selector 才有额外价值。

### 条件3：低成本观察能提前识别需求差异

选择器必须在昂贵计算前或中途知道：

```
当前请求是否值得继续
```

如果只有全部计算完才知道“这个请求需要什么”：

```
不能省掉昂贵计算
selector 没有计算控制收益
```

因此 RGC 需要证明：

```
合法、便宜、在线可见的状态
能预测后续动作价值
```

------

## 8.5 P 到 T 复用为什么可能省钱？

P 产生：

```
R = 候选相关历史表示
```

PT 直接读取 R。

只有以下条件都成立，才算真正节省：

```
P 和 PT 使用相同实际输入
P 和 PT 使用兼容参数
R 能稳定复用
重算费用 > 缓存读取/存储/校验费用
```

否则可能出现：

```
缓存管理成本 ≥ 重算成本
```

另外：

```
需求变化是否使 R 失效
```

由依赖决定，不由“需求变了”四个字自动决定。

在当前设计里：

```
R 不依赖 q
```

所以需求改变通常不使 R 本身失效；但依赖 q 的评分和 PT 结果需要重新计算。

------

## 8.6 STOP 为什么有价值？

继续计算只有在以下至少一项成立时才值得：

```
改善最终列表
改善后续选择
保持/恢复资源可行性
```

否则：

```
结果不变
费用增加
→ STOP
```

动态停止有额外价值，需要不同请求有不同停止位置：

```
A：G/P 已足够
B：必须 C
C：P 后继续 PT 才有收益
```

如果所有请求都应固定调用三步：

```
固定顺序更简单
selector 没有价值
```

------

## 8.7 REVIEW 为什么暂时不是主线？

需求审阅只有在以下条件同时成立时可能有用：

```
初始需求真的有错误/缺失
后续返回提供合法纠正证据
纠正会改变后续排序
收益 > 审阅 + 重算费用
```

以下情况不能证明 REVIEW 有价值：

```
来源变多
需求文本变长
列表发生变化
```

如果更小模型一次就能正确形成需求：

```
REVIEW 可以删掉
```

如果问题其实是排序器没学好：

```
改写需求未必解决
```

所以当前最小主线：

```
固定需求
关闭 REVIEW
先研究 P 后的 STOP/C/PT 选择
```

# 第8节的候选实现表

| 机制            | 解决什么                                 |
| --------------- | ---------------------------------------- |
| 结构化需求/LLM  | 把条件和历史假设表达给下游               |
| G/P/T/C         | 用不同方式提取公共、历史、内容、集合交互 |
| P→T 复用        | 避免重新计算 R                           |
| selector + STOP | 按请求分配计算、决定是否停止             |
| REVIEW          | 修正会影响排序的需求解释                 |

每一行都不是“自动必要”。

必须问：

```
对应哪个具体障碍？
更简单的 U/固定策略能否解决？
完整费用是否仍有优势？
```

------

# 第8节对你选择器工作的直接结论

你现在不需要证明：

```
G/P/T/C 架构理论上优于 U
```

你需要验证更窄的问题：

```
在已有 G/P/PT/C 排序器库中，
P 后状态 z 是否能预测：
C 或 EXTEND_T 相对 STOP 的质量增益与费用？
```

最小可证伪实验：

```
固定 q
关闭 REVIEW
先执行 G、P
比较：
  STOP
  C
  EXTEND_T
```

如果发现：

```
所有请求最优动作都相同
```

则 selector 没有额外价值，固定策略可能更好。

如果发现：

```
不同请求的最优动作确实不同
且 z 能提前预测
```

才值得训练 selector。
